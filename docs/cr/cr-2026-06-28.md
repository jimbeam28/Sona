## 2. Domain 层逻辑 BUG/FRAGILE

### 2.1 `play_queue.dart` — 播放队列模型

#### BUG-01: `==` 算子遗漏 shuffle 字段

**文件**: `lib/shared/models/play_queue.dart:288-294`
**问题**: `==` 算子不比较 `_shuffleOrder` 和 `_shufflePosition`。两个 shuffle 顺序不同的 PlayQueue 被视为相等，导致 Riverpod state 比较失灵——UI 不会重建。
```dart
// 288-294: 缺少 shuffle 字段
bool operator ==(Object other) =>
    identical(this, other) ||
    other is PlayQueue &&
        _listEquals(files, other.files) &&
        currentIndex == other.currentIndex &&
        startPositionMs == other.startPositionMs &&
        playMode == other.playMode;
    // 缺少: && _shuffleOrder == other._shuffleOrder
    //      && _shufflePosition == other._shufflePosition
```
**影响**: 高。Riverpod StateProvider 通过 `==` 判断是否通知 listener。shuffle 顺序变更可能被忽略。
**修复**: 在 `==` 和 `hashCode(:297-298)` 中加入两个 shuffle 字段。

#### FRAGILE-01: `withIndex` 不维护 shufflePosition 一致性

**文件**: `lib/shared/models/play_queue.dart:101-108`
**问题**: shuffle 模式下调用 `withIndex(3)` 会保留旧的 `_shufflePosition`。之后 `advanceShuffle()` 继续从旧排列的下一个位置取 index，而非从新 currentIndex 重新定位。
```dart
PlayQueue withIndex(int newIndex) => PlayQueue(
    files: files,
    currentIndex: newIndex,           // currentIndex 变了
    ...
    shuffleOrder: _shuffleOrder,      // 但 _shufflePosition 未更新
    shufflePosition: _shufflePosition, // → advanceShuffle 跳到旧序列的下一个
);
```
**影响**: 用户手动选曲后按"下一首"跳到意料之外的位置。
**建议**: 评估是否应将 `_shufflePosition` 重置为 `currentIndex` 在 shuffle order 中的位置（O(n) 查找），或保持当前"手动选曲打断 shuffle 序列"的设计但文档化。

### 2.2 `playback_orchestrator.dart` — 播放编排器

#### FRAGILE-02: 12 秒轮询等待播放开始

**文件**: `lib/features/player/domain/playback_orchestrator.dart:204-218`
**问题**: `loadAndPlay` 轮询等待 `player.playing == true`，每 200ms 检查一次，最多 60 次（12 秒）。大 FLAC 文件通过慢速 NAS 缓冲可能超时，即使播放恰好在超时后 1 秒开始。
```dart
for (int i = 0; i < 60; i++) {
    await Future<void>.delayed(const Duration(milliseconds: 200));
    if (player.playing) { playStarted = true; break; }
}
```
**影响**: 中。慢速网络下偶发"加载失败"。
**建议**: 将等待机制改为监听 `playerStateStream` 搭配超时，消除轮询。

#### FRAGILE-03: `saveProgress` 无 await（fire-and-forget）

**文件**: `lib/features/player/domain/playback_orchestrator.dart:352-363`
**问题**: `progressSaver.upsertProgress` 的 Future 未被 await。在 `dispose()` 后仍在执行的保存会静默失败。
**影响**: 低中。进度写入在正常路径下几乎总能完成，但 dispose 窗口期间可能丢进度。
**建议**: 考虑用 `unawaited` + `catchError` 记录异常。

#### FRAGILE-04: Shuffle 末尾过渡到随机选取

**文件**: `lib/features/player/domain/playback_orchestrator.dart:247-262`
**问题**: `advanceShuffle()` 到排列尾部返回 null 后，fallback 调用 `play_mode.nextIndex` 做纯随机选取（可能重复已播曲）。用户预期是循环排列或停止——而不是切换到随机盲选。
**影响**: 中。Shuffle 用户体验不直觉。
**建议**: 排列播完后循环重排（`Fisher-Yates reshuffle`）而非随机选。

### 2.3 `play_mode.dart` — 播放模式

#### FRAGILE-05: shuffle `previousIndex` 返回随机 index

**文件**: `lib/features/player/domain/play_mode.dart:109-116`
**问题**: 对于 shuffle 模式，`previousIndex` 返回一个随机不同的 index，而非真正的"上一首"。只有在 `advanceShuffle()`/`retreatShuffle()` 历史边界外才被调用，但语义让人困惑。
**影响**: 低。边界情况（shuffle 排列开头按上一首）概率低。
**建议**: 文档明确说明这是 fallback 行为；或改为 wrap 到排列尾部。

### 2.4 `progress_policy.dart` — 进度策略

#### FRAGILE-06: 刚过 10s 的文件 cleared 阈值过激

**文件**: `lib/features/progress/domain/progress_policy.dart:22-28`
**问题**: `durationMs = 10001` 时，阈值 `10001 - 10000 = 1`，`positionMs > 1`（即 >= 2ms）就触发 `shouldClear = true`。10-15 秒的短音频文件，任何播放位置 >= 5s（`shouldSave` 阈值）都导致进度被清除而非保存。
```dart
// 边界: durationMs=10001 → positionMs > 1 就 cleared
bool shouldClear(int positionMs, int? durationMs) {
    if (durationMs == null) return false;
    if (durationMs <= 10000) return false;   // 10s 整及以下被保护
    return positionMs > durationMs - 10000;  // 10001-10000=1 → 过激
}
```
**影响**: 中。短语音/有声书片段（10-15s）的进度无法保存。
**建议**: 增加阈值保护，例如 `positionMs > durationMs - max(10000, durationMs * 0.1)`。

### 2.5 `playlist_service.dart` — 播放单

#### BUG-02: `addTracksToPlaylist` 缺少内存内去重

**文件**: `lib/features/playlist/domain/playlist_service.dart:64-81`
**问题**: 每个文件通过 `trackExists` 查询数据库判重，但 `tracks` 列表中的中间结果不互查。同一文件在输入中出现两次时（UI 快速双击），两次 `trackExists` 均返回 false（都还没写入 DB）→ 产生重复。
```dart
// 第 67-77 行: 逐文件查 DB，但同文件第二次出现时 DB 尚无记录
for (final file in files) {
    final exists = await _dao.trackExists(playlistId, file.path);
    if (!exists) { tracks.add(...); }
}
```
**影响**: 高。重复曲目会出现在播放单中。
**修复**: 加 `final seen = <String>{};`，像 `importPlaylist`（`:152`）一样在内存中做 `seen.add(file.path)`。

### 2.6 `timer_service.dart` — 定时器状态机

#### BUG-03: `resume()` 四舍五入到分钟导致精度损失

**文件**: `lib/features/timer/domain/timer_service.dart:214-216`
**问题**: `resume()` 将保存的毫秒剩余用 `(ms / 60000).ceil()` 转为分钟，每次暂停/恢复循环都会向上取整，累积误差可达 30-59 秒。
```dart
// ms=30000 (30s) → (30000/60000).ceil() = 0.5.ceil() = 1 → 恢复 60s！
final minutes = (ms / 60000).ceil();
_state = TimerState(mode: TimerMode.duration,
    endTime: now.add(Duration(minutes: minutes)), // 多了 30s
);
```
**影响**: 高。每次 pause/resume 增加数十秒。用户发现定时器不准。
**修复**: 直接使用 `Duration(milliseconds: ms)`：
```dart
_state = TimerState(
    mode: TimerMode.duration,
    endTime: now.add(Duration(milliseconds: ms)),
    ...
);
```

## 3. Provider 层审计

### 3.1 资源泄漏风险

#### ISSUE-P1: `_startAutoSaveProvider`/`_startPauseSaveProvider` 缺少 `ref.onDispose`

**文件**: `lib/features/player/player_provider.dart:199-217`
**问题**: `startProcessingListenerProvider`（`:228`）有 `ref.onDispose` 取消订阅，但自动保存（`:199`）和暂停保存（`:208`）的 provider 没有。ProviderScope 被处理时定时器/订阅继续运行。
```dart
final _startAutoSaveProvider = Provider<void Function()>((ref) => () {
    ref.read(_autoSaveTimerProvider)?.cancel();
    ref.read(_autoSaveTimerProvider.notifier).state = Timer.periodic(
        const Duration(seconds: 10), (_) => ref.read(saveProgressProvider)());
    // 缺少: ref.onDispose(() { ref.read(_autoSaveTimerProvider)?.cancel(); });
});
```
**影响**: 中。ProviderScope dispose（如测试 tearDown）后定时器可能触发已释放 provider。

### 3.2 一致性

#### ISSUE-P2: `main.dart` 绕过 shared/di/providers.dart

**文件**: `lib/main.dart:19-20`
**问题**: 直接 import `features/browser/browser_provider.dart` 和 `features/player/player_provider.dart`，而非通过 `shared/di/providers.dart` 桥接。
```dart
import 'features/browser/browser_provider.dart';  // 应通过 bridge

```
**影响**: 低。main.dart 是入口文件，实践上合理但模式不统一。

#### ISSUE-P3: `onQueueChanged` 是可变公开字段

**文件**: `lib/features/player/domain/playback_orchestrator.dart:92`
**问题**: `onQueueChanged` 回调未用 `final` 保护，可被覆盖。
```dart
void Function(PlayQueue?)? onQueueChanged;  // 公开可变 → 可能被覆盖
```
**影响**: 低。项目中仅有 player_provider.dart 写一次。

#### ISSUE-P4: `persistQueueOnChangeProvider` 每次队列变更都写 SharedPreferences

**文件**: `lib/features/browser/browser_provider.dart:117-131`
**问题**: 每次队列变化（切歌、前进、删除）都触发 `jsonEncode + setString`。快速切歌时产生序列化开销。
**影响**: 低。SharedPreferences 内部异步写入，实际影响小。但建议加去抖。
